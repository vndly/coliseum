### [a/error-handling/verdict-takeover/single-offer-abandons-settled-bowl] The takeover is offered once, by one seat; if that offer is not made or fails, the bowl is never judged

- **Location:** `frontend/src/components/screens/match_screen.vue:588` (`runTakeover`), `:610` (single-seat restriction), `:615` (the un-retried `catch`), `:575` (one-shot arming); related: `frontend/src/match/match_client.ts:280` (`primed`).
- **Severity:** High
- **Confidence:** Medium
- **Defect:** `runTakeover` restricts the offer to exactly one seat — the `nextActivePlayer` — and consumes its single armed timer whether or not a verdict results. Its `submitVerdict` call has only a `.catch` that writes to the error line; there is no retry and no re-arm. Nothing else ever arms `takeoverTimer` again for that throw. If the designated seat's write is rejected, or that seat never armed a takeover in the first place, the settled bowl stays unjudged: `verdict.seq` never reaches `throwSeq`, so `judged` is false forever, which makes `canThrow`, `canPass` and `botMove` false for _every_ player. The thrower's hand also stays charged, since dice are debited at throw time and repaid only by the verdict.
- **Trigger:** Two established paths. (1) The designated seat's `submitVerdict` transaction rejects — a dropped connection or exhausted contention retries — and it never tries again. (2) The designated seat is a client that reloaded during the throw: `MatchClient.listen` consumes the first server delivery of the throws query as history and sets `primed` afterwards (`match_client.ts:280-292`), so a reloaded client never runs that throw through its scene, never fires `onSettled`, and never arms a takeover for it. If the thrower has also gone, nobody judges the bowl.
- **Evidence / verification:** Traced every exit from `runTakeover`; none re-arms. Confirmed `takeoverTimer` is assigned only at `:578`. Confirmed the `catch` at `:615` only sets `error.value`. Refutation attempt: I checked whether another player could step in — `:610` returns unless this client _is_ the `nextActivePlayer` seat, so no second offer exists by construction; and whether `runTransaction`'s internal retries cover the rejection — they cover contention, not a dropped connection, which still surfaces as a rejection to the caller. Two guards the design does rely on were confirmed sound and are not part of this defect: the in-transaction idempotency check at `match_client.ts:406` correctly re-reads `throwSeq` and `verdict.seq`, and `bowlVersion` is counted from that read rather than blindly incremented. The residual uncertainty is only how often a verdict write actually fails in practice, which is why this is Medium confidence rather than High.
- **Suggested fix:** Re-arm the timer on every path that abandons the offer, and retry a rejected `submitVerdict` with backoff. Widen the offer after a further timeout so that a second seat can step in when the first is gone — the transaction already makes a duplicate attempt harmless.

### [a/error-handling/match-connection/unreadable-snapshot-dropped-silently] An absent, deleted, or unparseable match is dropped without a word, leaving the screen connecting forever or frozen while still interactive

- **Location:** `frontend/src/match/match_client.ts:248` (`onSnapshot` with no error callback, null parses discarded), `:264` (same for the throws query); related: `frontend/src/components/screens/match_screen.vue:306` (`waitingLine`), `:299` (`showWaiting`), `:411` (`onState`).
- **Severity:** Medium
- **Confidence:** High
- **Defect:** `listen` calls `onState` only `if (state !== null)`, and passes no `onError` to either `onSnapshot`. A document that does not exist yields `snapshot.data() === undefined`, which `parseMatchState` refuses, so the callback never fires and `state.value` stays `null` — `waitingLine` reads "Connecting to the match" indefinitely, with no timeout and no error. A listener that fails permanently (a rules denial, a missing index) is equally invisible: the SDK tears the stream down and nothing in the app learns of it or reconnects. When a document is deleted or edited into an unparseable shape _mid-match_, the last good state is retained instead, so the rail, the turn indicator and the throw controls all stay live over a match that no longer exists; the player can throw, and only then does the write fail. This directly contradicts the stated intent at `frontend/src/match/match_state.ts:9-13`, that a half-written or hand-edited document "should leave a player looking at 'no such match'".
- **Trigger:** Open `/match/<code>` for a code that is not a match — a mistyped or stale shared link, or a bookmark to a match that has since been removed. The route is explicitly designed to be shared (`frontend/src/router.ts:18-19`), so this is an ordinary path, not an adversarial one. For the frozen-but-interactive variant, delete or corrupt the document while a match is in progress.
- **Evidence / verification:** Read `listen` in full and confirmed both listeners are registered with a single success callback and no second argument. Confirmed `state` is assigned only inside `onState` (`match_screen.vue:434`), so no failed read can clear it. Confirmed `waitingLine` has no other branch for the null case. Refutation attempt: I checked whether the in-app join path protects the user — it does: `MatchClient.join` refuses a nonexistent code inside its transaction and the lobby surfaces "No match with that code." before navigating, so the lobby never sends anyone to a dead match. Direct URL entry bypasses `join` entirely, which is what leaves the case uncovered. Also noted a worse rendering of the same defect: with `?bots=1` on the query string, `showWaiting` is false while `state` is null (`:299-301`), so the screen renders the match chrome over an empty bowl with no card, no line and no error at all.
- **Suggested fix:** Give both `onSnapshot` calls an error callback that surfaces the failure through the existing `error` ref. Distinguish "document does not exist" (`snapshot.exists()` is false) from "document did not parse" and report each, rather than discarding both.

### [b/validation-and-coercion/match-parsing/index-and-length-fields-unbounded] The parse boundary bounds most fields it hands on but leaves four that can freeze or blank a match

- **Location:** `frontend/src/match/match_state.ts:551` (`turnIndex`), `:554` (`bowlVersion`), `:366` (`verdict.seq`), `:484` (`readPlayers`), `:336` (`readStrings` for `removed`/`returned`); compare the bounded readers at `:298` (`readSeatCount`), `:406` (`readHand`), `:465` (`readBowl`), `:272` (`readFace`).
- **Severity:** Medium
- **Confidence:** High
- **Defect:** `parseMatchState` states as its purpose that anything becoming an index, a length or a body count is refused rather than repaired. Four fields escape that: `turnIndex`, `bowlVersion` and `verdict.seq` are checked only for being finite numbers, and `players` and the verdict's `removed`/`returned` identifier lists are not length-bounded at all. Each has a distinct, silent consequence. A non-integer or out-of-range `turnIndex` makes `state.players[turnIndex]` undefined on every client, so `activePlayer` is null, nobody's `isMyTurn` is true, and neither a pass nor a takeover can recover it. A `bowlVersion` of exactly `-1` collides with the `appliedBowlVersion = -1` sentinel at `match_screen.vue:65`, so the equality check at `:439` returns early on the very first snapshot and the bowl is never handed to the scene — the player sits at an empty table for the whole match. A `verdict.seq` above `throwSeq` permanently satisfies the idempotency guard at `match_client.ts:406` while permanently failing the `judged` equality at `match_screen.vue:119`, so no bowl is ever judged again and `onThrow` drops every incoming throw at `:475`. An unbounded `players` array is rendered one row per entry and walked by `nextActivePlayer` and `survivingPlayer` on every verdict, and `parseMatchState` runs on _every_ match the lobby lists.
- **Trigger:** A match document written by anything other than this game. The file's own header names this threat model explicitly — matches are keyed by a four-character code, every lobby match is publicly listed with its code (`open_matches.ts:153`), and the code's own comment states the security rules are permissive.
- **Evidence / verification:** Read every reader in `match_state.ts` and confirmed the asymmetry against the four bounded ones. Traced each field to its consumer and confirmed the stated outcome: the `-1` sentinel collision at `match_screen.vue:65`/`:439`, the `judged` equality at `:119`, the guard at `match_client.ts:406`, and `state.players[state.turnIndex]` at `rules.ts:258`. Refutation attempt: I confirmed nothing _throws_ — every downstream read uses `?? null` or `?? []`, and `nextActivePlayer`'s loop is bounded and returns `from` when it resolves nothing — so the failure is a silent, unrecoverable freeze rather than a crash, which is precisely the outcome the boundary exists to prevent. I also confirmed the game itself never writes these values: `turnIndex` is only ever `0` or a `nextActivePlayer` result, and `bowlVersion` is only ever counted upward from a transactional read. The remaining assumption is that a third party can write these documents at all, which rests on the permissive-rules claim in the source comments and could not be verified from this repository.
- **Suggested fix:** Bound `turnIndex` to an integer in `[0, players.length)`, `bowlVersion` and `throwSeq` and `verdict.seq` to non-negative integers, `players` to `MAX_PLAYERS`, and `removed`/`returned` to `MATCH_DICE` — the same treatment `readBowl` and `readHand` already apply. Separately, move `appliedBowlVersion`'s sentinel out of the value domain (a `null`, or a separate boolean) so no stored number can collide with it.

### [a/logic-errors/die-face-reading/face-published-from-unsettled-die] The settle timeout publishes an authoritative face read off a die that may still be moving

- **Location:** `frontend/src/scene/dish_scene.ts:470` (`atRest || this.throwing >= SETTLE_TIMEOUT`), `frontend/src/scene/die.ts:246` (`face: readDieFace(attitude)`), `frontend/src/scene/die_state.ts:126` (strict `>` tie-break); related: `frontend/src/scene/dimensions.ts:313`, `frontend/src/match/rules.ts:262`.
- **Severity:** Medium
- **Confidence:** Medium
- **Defect:** After `SETTLE_TIMEOUT` (10 seconds of simulated time) the scene declares the throw over and calls `onSettled` regardless of whether the dice have actually stopped. That leads straight to `submitVerdict(seq, scene.bowlSnapshot, …)`, and `bowlSnapshot` reads each die's _current_ rotation through `readDieFace` with no rest check of any kind. A die still tumbling at that instant publishes whatever face happens to be uppermost mid-rotation. The same reader also resolves a tie by list order — a die wedged on an edge with two face normals at equal height silently reports the lower-indexed value. The published `face` is authoritative for the whole table: every other client reads the stored value and never recomputes it (`match_state.ts:315-330`), and `resolveThrow` judges on it, so the die is removed as a six or paired on a value nobody can see.
- **Trigger:** Any bowl that has not settled within 10 seconds of simulated time — a die wedged between others or standing against the wall and still creeping. The timeout exists precisely because the authors expect bowls that do not settle; what is missing is a guard on the face read once that path is taken.
- **Evidence / verification:** Traced the chain `dish_scene.ts:470 → onSettled → match_screen.vue:568 submitVerdict → scene.bowlSnapshot → dice.ts:148 → die.ts:246 → readDieFace`, confirming no rest or confidence check anywhere along it. Confirmed both `deltaTime` (`dish_scene.ts:438`) and the physics accumulator (`physics_world.ts:129`) are clamped to `MAX_FRAME_TIME`, so the 10 seconds is simulated rather than wall-clock and a backgrounded tab cannot shorten it. Refutation attempt: I checked whether this can desynchronise clients — it cannot, since only the thrower reads a face and everyone else accepts the stored one, so the table stays consistent while being consistently _wrong_. A parallel refutation established that the bowl's own geometry cannot hold a cocked die unaided: the fillet from `(4.10, 0.53)` to `(4.45, 0.90)` reaches roughly 45°, where the required friction exceeds the die/bowl product of 0.55, so a lone die slides to the flat floor — the case therefore needs a die-on-die wedge. The remaining uncertainty is how often a real bowl fails to settle inside the timeout, which is why this is Medium confidence.
- **Suggested fix:** Record whether the settle was genuine or timed out, and on a timeout either refuse to publish and retry, or snap each die to its nearest resting attitude before reading it. Additionally, have `readDieFace` report the margin between the best and second-best normal so a near-tie can be detected rather than silently resolved by list order.

### [a/concurrency/throw-submission/second-view-overwrites-throw-record] A second view of the same match races the same seats and silently overwrites throw records

- **Location:** `frontend/src/match/match_client.ts:343` (`batch.set` on `throws/{seq}`), `frontend/src/components/screens/match_screen.vue:511` (`seq = match.throwSeq + 1`); related: `frontend/src/components/screens/match_screen.vue:211` (`botMove`), `:629` (`runBotTurn`), `frontend/src/match/bots.ts:9-14`.
- **Severity:** Medium
- **Confidence:** Medium
- **Defect:** The throw record is written with an unconditional `set` at a document id derived from a _cached_ `throwSeq + 1`, with no create-only precondition and no transaction. Firebase anonymous auth is shared per origin, so the same match opened in two tabs of one browser is the same seated player twice. Both tabs pass the seat check, both render the match, and — because nothing designates a host — both drive every bot seat, contrary to the invariant stated at `bots.ts:9-14` that a bot's turns are played by "the browser that started the match". When both compute the same `seq` before either write round-trips, the second `set` overwrites the first record with different dice. The authoritative bowl then comes from whichever tab's `submitVerdict` wins, while the throw record every _other_ player animates holds the other tab's dice — so the table watches one throw and is teleported onto the result of a different one.
- **Trigger:** Open the same match in two tabs (duplicating a tab is enough). In a bot match the race recurs on every bot turn, because each tab draws an independent 600–1400 ms pause before acting and the guard that would suppress the second only closes once the first write has propagated.
- **Evidence / verification:** Read `submitThrow` in full and confirmed `batch.set` with no `exists` precondition, and `batch.update` writing `throwSeq`, `hasThrown` and `pools.{thrower}` unconditionally. Confirmed `seq` is derived at `match_screen.vue:511` from the cached snapshot. Confirmed `botMove`/`runBotTurn` check only match state, never which browser created the match. Refutation attempt: I bounded the damage rather than dismissing it. The pool write is not double-charged, because both tabs compute the same `kept` from the same cached hand and the write is idempotent. `submitVerdict`'s transaction guarantees exactly one verdict counts, so the stored match state converges and is not corrupted. What remains is a lost throw record and a replay that does not match the judged bowl — real incorrect behavior, not state corruption, which is why this is Medium and not High.
- **Suggested fix:** Write the throw record with a create-only precondition so a duplicate `seq` fails loudly instead of overwriting, and derive `seq` inside a transaction that re-reads `throwSeq`. Separately, elect a single driver for bot seats — for example the client whose uid matches `players[0]`, or a claim written into the document — so two views of one bot match cannot both act.

### [c/api-or-library-misuse/throw-gesture/release-off-table-plane-discards-throw] Releasing an aim above the horizon silently discards a fully previewed throw

- **Location:** `frontend/src/scene/throw_controller.ts:301` (`onPointerUp` requires a fresh projection), `:284` (`onPointerMove` keeps the last good one), `:399` (`projectToTable`).
- **Severity:** Medium
- **Confidence:** Medium
- **Defect:** The two halves of the gesture disagree about what to do when the release ray misses the table plane. `onPointerMove` returns early on a failed projection, deliberately leaving `launchGround` and the drawn preview at the last valid value, so the player goes on seeing a good aim line. `onPointerUp` instead _requires_ a fresh successful projection and, on failure, falls through to `cancel()` — no throw is made, no feedback is given, and the preview simply vanishes. The player aims, sees a valid line, releases, and nothing happens.
- **Trigger:** `Ray.intersectPlane` returns null whenever the ray points at or above the horizon. Pointer capture keeps the drag live outside the canvas and NDC coordinates extrapolate, so the horizon is crossed at roughly 42% of a half-height above the canvas top at the maximum camera elevation — an ordinary mouse drag. On a narrow portrait viewport the lens widens to `CAMERA_MAX_FIELD_OF_VIEW`, which brings the horizon _inside_ the canvas, so a band across the top of the screen neither starts an aim nor completes one.
- **Evidence / verification:** Read both handlers and `projectToTable` directly and confirmed the asymmetry: the move path's `if (!this.projectToTable(...)) { return }` versus the up path's `if (this.projectToTable(...)) { …launch… } cancel()`. Refutation attempt: I checked for an earlier guard that would save it — `clampToThrowRadius` never runs on this path, and `aimRaycaster` succeeds because the canvas bounds are non-zero, so the failure is purely the plane test; and I confirmed it fails safe, producing no bad throw, which caps the severity at a lost gesture rather than a wrong one. The residual uncertainty is the exact on-screen extent of the affected band, which depends on viewport aspect and camera elevation and was derived geometrically rather than measured in a browser.
- **Suggested fix:** Have `onPointerUp` fall back to the last valid `launchGround` exactly as the preview already does, rather than requiring a fresh projection. Failing that, cancel the aim visibly the moment the projection starts failing, so the preview never shows a line that cannot be thrown.

### [a/resource-management/scene-teardown/webgl-context-never-released] Repeated match visits accumulate live WebGL contexts

- **Location:** `frontend/src/scene/dish_scene.ts:415` (`dispose`).
- **Severity:** Low
- **Confidence:** Medium

Refutation attempt: the canvas is dropped by Vue and browsers do reclaim contexts on garbage collection, and the cap is handled by force-losing the oldest rather than by failing outright, so the practical impact is bounded and intermittent — which is why this is Low severity and Medium confidence rather than a confirmed user-visible failure.
- **Suggested fix:** Call `renderer.forceContextLoss()` immediately before `renderer.dispose()`.
